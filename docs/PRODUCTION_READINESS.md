# Production Readiness — Ma Yai On POS

สถานะเอกสารนี้อิงจากการตรวจซอร์สโค้ด ไม่ใช่ผลทดสอบบนเครื่องจริง

## สิ่งที่แก้ในรอบนี้

- งาน retry ของ DataHub จะพกรหัสร้านที่สร้างงานไว้ใน WorkManager input data ไม่พึ่งเฉพาะรหัสร้านที่กำลัง active ใน SharedPreferences อีกต่อไป งานเก่าที่ไม่มี input data ยัง fallback ไปใช้ค่าเดิมเพื่อความเข้ากันได้
- การอ่าน backup จาก Firestore ตรวจว่า `recordId` ตรงกับ document ID และ `storeId` ตรงกับ store path หากมีค่าในเอกสารที่ขัดแย้ง จะปฏิเสธชุด restore แทนการนำข้อมูลที่ระบุตัวตนไม่ตรงกันเข้าฐานข้อมูล

การแก้ไขนี้ไม่เปลี่ยนชื่อฐานข้อมูล SQLite, schema, หรือคำสั่งลบข้อมูลเดิม

## สถานะก่อนใช้งานกับข้อมูลร้านจริง

| ระบบ | สิ่งที่ยืนยันได้จากโค้ด | สิ่งที่ยังต้องทดสอบ/แก้ก่อน production |
|---|---|---|
| SQLite / DataHub | มีฐานข้อมูล `data_hub.db` และตาราง `hub_records`; การ upgrade ปัจจุบันไม่ลบข้อมูล | ตรวจว่าหน้าจอขายและสต๊อกทุกหน้าบันทึก/อ่านผ่านแหล่งข้อมูลที่ถูกต้อง และตรวจการย้าย schema ในอนาคต |
| Cloud backup | บันทึก local ก่อน แล้วจึงส่งขึ้น Cloud; มีสถานะ pending/failed และ WorkManager retry | ทดสอบเน็ตหลุด, process ถูกปิด, timeout, 500+ records, และตรวจว่าไม่มีรายการค้างหลัง retry |
| Restore / ย้ายเครื่อง | restore แทรกเฉพาะ record ที่ไม่มีในเครื่อง; ตรวจ identity ของ record กับ Firestore path | ทดสอบบนเครื่องที่สองโดยเทียบจำนวนรายการและยอดขาย/สต๊อก/ลูกหนี้กับเครื่องต้นทาง |
| การยืนยันตัวตน/สิทธิ์ | แอปปัจจุบันใช้ Firebase Anonymous Authentication และรับ store ID จากผู้ใช้ | **BLOCKER:** store ID ไม่ใช่ credential ต้องมีบัญชีร้านหรือ trusted backend ที่ผูกสมาชิกกับร้าน และต้องตรวจ Firestore Security Rules ที่ deploy จริง |
| ข้อมูลระหว่างหลายเครื่อง | มี revision check สำหรับ cloud upload | ทดสอบแก้ record เดียวกันพร้อมกัน, ความขัดแย้งของ revision, และธุรกรรมสต๊อก/การขายแบบ concurrent |
| นโยบายลบข้อมูลเก่า | มี retention guard และตรวจ sync state/revision ก่อนลบ | ทดสอบข้อมูลตัวอย่างและยืนยันสำเนา/ประวัติครบก่อนเปิดใช้กับฐานข้อมูลจริง |
| Build | GitHub Actions เคย build debug APK ผ่านใน commit ก่อนหน้า | ต้องให้ Actions build commit ของ branch นี้อีกครั้ง; build ผ่านไม่แทน functional/device test |
| POS / อุปกรณ์ | มีหน้าจอขาย, สต๊อก, ลูกหนี้, บาร์โค้ด, รายงาน และเครื่องพิมพ์ในโปรเจกต์ | ต้องทดสอบ flow end-to-end บน Android และอุปกรณ์จริง โดยเฉพาะสแกนบาร์โค้ด, พิมพ์ซ้ำ, ชำระบางส่วน และการยกเลิกรายการ |

## Acceptance checklist ที่ต้องผ่านก่อนเปิดร้านจริง

- [ ] ติดตั้งใหม่บนเครื่องทดสอบและเชื่อมต่อร้านผ่านกระบวนการยืนยันตัวตนที่ปลอดภัย
- [ ] กู้คืนบนเครื่องที่สองและเทียบจำนวน record กับยอดรวมจากเครื่องต้นทาง
- [ ] ยืนยันว่า restore ไม่เขียนทับ local record ที่มีอยู่
- [ ] บันทึกขาย/รับสินค้า/ชำระหนี้ขณะ offline แล้ว reconnect; ทุก record ต้อง sync สำเร็จหรือแสดงสถานะผิดพลาดชัดเจน
- [ ] ทดสอบ backup มากกว่า 500 records และสลับร้านก่อน worker ทำงาน
- [ ] ทดสอบบัญชีร้านอื่นอ่านหรือเขียน backup ไม่ได้ ด้วย Firestore Rules ที่ deploy จริง
- [ ] ทดสอบการขายและตัดสต๊อกซ้ำ/พร้อมกันจากสองเครื่อง และตรวจยอดคงเหลือ
- [ ] ทดสอบชำระหนี้เต็มจำนวน/บางส่วน/ยอดผิดพลาด และตรวจประวัติการรับชำระ
- [ ] ทดสอบบาร์โค้ดซ้ำ, เครื่องพิมพ์ offline, พิมพ์ใบเสร็จซ้ำ และการกู้คืนหลังปิดแอป
- [ ] ทดสอบ retention ด้วยข้อมูลจำลอง พร้อมตรวจประวัติและ backup ก่อน/หลังลบ
- [ ] ติดตั้ง APK จาก Actions บนอุปกรณ์ Android จริงและบันทึกผลทดสอบ
- [ ] สำรองข้อมูลและมีแผน rollback ที่ทดลองใช้ได้ก่อนนำข้อมูลจริงเข้าระบบ

## ข้อจำกัดที่ยังเปิดอยู่

ไม่สามารถทำให้ระบบปลอดภัยครบถ้วนด้วยการแก้ Android client อย่างเดียวได้ เพราะการอนุญาตอ่าน/เขียนข้อมูลร้านต้องบังคับใช้ฝั่ง Firestore Security Rules หรือ trusted backend ด้วย ขณะนี้ยังไม่มีหลักฐานใน repository นี้ที่ยืนยัน rules และ membership configuration ที่ deploy ใน Firebase project จริง จึงห้ามถือว่า cloud backup/restore พร้อม production จนกว่าจะมีการตั้งค่าและทดสอบส่วนนี้

ไม่ควรใช้ข้อมูลร้านจริงจนกว่า blocker ด้านสิทธิ์เข้าถึงและ acceptance checklist จะผ่าน ห้ามถือว่า build สำเร็จเป็นหลักฐานว่าแอปทำงานจริงครบทุกระบบ
